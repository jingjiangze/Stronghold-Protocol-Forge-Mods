上传 mod

提 PR 到 mod 仓库 → CI 自动校验 → 维护者审核通过才合并。不需要装 git，也不需要任何 token。

三步走

① Fork + 上传 ② CI 自动校验 ③ 等维护者审核 GitHub 网页 mod-gate / mod-compat 缺审批时 PR 是 blocked 放 incoming/<名字>/ 约 1–2 分钟 合不了 —— 必须人批
① 去 Fork → 直接上传页（小包）

小包（≤25 MiB）用网页即可；大包（25–100 MiB）用 git push 到你自己的 fork（不需要 token）。

方式 A：GitHub 网页（≤ 25 MiB，推荐）

  1. 打开 mod 仓库，点右上角 Fork → Create fork（fork 到你自己的账号下）。
  2. 进你 fork 里的 incoming/ 目录 → Add file ▾ → Create new file。
  3. 文件名填 incoming/<你的 mod 名字>/SOURCE.md —— 打斜杠会自动建目录。 内容照抄 SOURCE 模板 填好五件事。
  4. 回到 incoming/<你的 mod 名字>/ → Add file ▾ → Upload files → 把 mod.zip 拖进去。 （支持直接拖整个文件夹）
  5. 点 Commit changes，GitHub 会引导你 Create pull request 回原仓库。
  6. 等 mod-gate 变绿，然后 等维护者审核。在那之前 PR 显示 Review required，合不了。

方式 B：git（25–100 MiB）

推到你自己的 fork，不需要任何 token（fork 是你自己的仓）：

git clone https://github.com/<你的账号>/Stronghold-Protocol-Forge-Mods.git
cd Stronghold-Protocol-Forge-Mods
mkdir -p "incoming/<你的 mod 名字>"
cp /path/to/mod.zip "incoming/<你的 mod 名字>/"
# 照着模板写 incoming/<你的 mod 名字>/SOURCE.md（五件事）
git add "incoming/<你的 mod 名字>"
git commit -m "上传 <你的 mod 名字>"
git push

然后在 GitHub 上开 PR 回 jingjiangze/Stronghold-Protocol-Forge-Mods 的 master。

方式 C：上传站（不想碰 GitHub 时）

  1. 打开 上传站，填「mod 名 + 备注」，选 zip，点上传（≤100 MiB）。
  2. 会给你一个 认领码（只显示一次，存好）——用它可改包、撤回。
  3. 维护者审过后，用服务端「过审 → 代提 PR」推进仓库，再走同一条 CI + 审核 + 合并。
这条不是主路径。上传站要把包转手一次，比直接提 PR 多一道人工。 能用方式 A/B 就用它们。

上传规范（必读）

一、包的形态

  • 一个 mod 一个目录；目录名 = mod 名字，不要多套一层。
  • pack.json（工坊包）或 plugin.json（插件包）必须放在 zip 根；允许一层包裹目录。
  • 单个文件 ≤ 32 MB（引擎 zip 读取上限；超了引擎自带导入路径会拒收）。
  • 整个 zip ≤ 200 MiB（引擎 PLUGIN_LIMITS.pluginBytes）。

二、SOURCE.md 要写清的五件事

  • 原件叫什么、从哪来（可追溯的链接或来源）。
  • 原作者是谁（用原作者的名字，不要写成你的）。
  • 原件的许可（如 GPL-3.0-or-later / 未声明）。
  • 你改了什么：具体到文件、数据、数值，不要只写「优化了一些东西」。
  • 自带素材哪来的（自绘 / 从游戏客户端导出 / 第三方，各自标注）。

三、素材与版权

  • 夹带游戏官方素材照收，但必须如实标注 —— 未标注才是问题。
  • 含官方素材的包会在站上醒目标记，并写明「版权归鹰角网络 / Yostar，仅供非商业个人使用」。
  • 原作者明确禁止再分发的，不要提交。

四、CI 会自动挡掉的

判据含义
类型认不出zip 中央目录里既无 pack.json 也无 plugin.json
整档 CRC 失败zip 损坏（传输中断 / 重复压缩）
超过 200 MiB引擎装载上限
索引不一致改了 mods/ 下 zip 却没同步 mods/index.json

五、维护者审核会看什么

  • 署名对不对（原作者 ≠ 兼容改写者，要分开写）。
  • 说明包里有没有说清「装上会生效什么」—— 说明包不收，只收能装的真功能包。
  • 会不会和存量包撞 pack.json 的 id（引擎不允许同 id 并存）。
CI 绿 ≠ 已审核。它只能证明「形状对、没损坏」，装不装得上还要维护者在引擎里实测。 合并前缺审批时 GitHub 会直接拦住。

本地自查（可选）

用管理器自带的校验器先过一遍，能和 CI 判据对齐：

node tools/mod.mjs check <包目录或 zip>      # 只出报告，不写文件
node tools/mod.mjs import <包> --dry-run     # 看类型与 blocker
提 PR 后 CI 会跑 mod-gate（类型 / CRC / 大小 / 索引一致性）与 mod-compat（静态契约预检）。 两者都绿 + 维护者审批通过，才允许合并。
