上传 mod

提 PR 到 mod 仓库 → CI 自动校验 → 维护者审核通过才合并。不需要装 git，也不需要任何 token。

① Fork

复制到你自己的账号

在 GitHub 点一下 Fork，得到属于你的副本。之后的改动都发生在你自己的仓里。

② 上传

放进 incoming/

目录名用 mod 的名字，里面放 mod.zip 与 SOURCE.md（写清五件事）。

③ 等审核

CI 绿了也还合不了

CI 只证明「包没坏」。缺维护者审批时 PR 显示 Review required，GitHub 直接拦住。

方式 A · GitHub 网页（推荐）

  1. 打开 mod 仓库，点右上角 Fork → Create fork。
  2. 进你 fork 里的 incoming/ → Add file ▾ → Create new file。
  3. 文件名填 incoming/<mod 名字>/SOURCE.md —— 打斜杠会自动建目录。 内容照抄 SOURCE 模板。
  4. 回到该目录 → Add file ▾ → Upload files → 把 mod.zip 拖进去（支持拖整个文件夹）。
  5. Commit changes → GitHub 会引导你 Create pull request 回原仓库。
  6. 等 mod-gate 变绿，然后等维护者审核。
① 去 Fork 直接打开上传页
为什么 fork 而不是直接改？你没有原仓库的写权限——这是设计如此。fork + PR 让改动先经 CI 与人工审核，才进入公开站。
传完请核对文件列表。把 mod.zip 与 SOURCE.md 都拖进去后， 确认提交页的文件清单里两个都在再点提交。若 zip 没出现在清单里，说明它被忽略了 —— 换方式 B（git）或方式 C（上传站）。
PR 合并 ≠ mod 已上线。合并后包落在仓库 incoming/ 里等维护者处理； 要让它出现在上面这个站上，还需维护者做完兼容、经上传站审核上线。

方式 B · git（25–100 MB）

推到你自己的 fork，不需要任何 token（fork 是你自己的仓）：

这条路有两个前提：① 本机装了 Git；② git clone 会下载整个仓库（约 60.9 MB）。 不满足的话，超过 25 MB 请用方式 C（上传站）。 
git clone https://github.com/<你的账号>/Stronghold-Protocol-Forge-Mods.git
cd Stronghold-Protocol-Forge-Mods
mkdir -p "incoming/<mod 名字>"
cp /path/to/mod.zip "incoming/<mod 名字>/"
# 照着模板写 incoming/<mod 名字>/SOURCE.md（五件事）
git add "incoming/<mod 名字>"
git commit -m "上传 <mod 名字>"
git push
推完请确认 zip 真的在列表里。本仓的 .gitignore 忽略 *.zip， 已为 incoming/、mods/、packs/ 三处开了放行。 若 git status 里看不到你的 mod.zip，说明放行规则被改坏了 —— 那就先别推，开 issue 告知。

然后在 GitHub 上开 PR 回 jingjiangze/Stronghold-Protocol-Forge-Mods 的 master。

大包走 git 而不是网页，是因为 **GitHub 网页上传单文件上限 25 MB**（平台硬限，绕不过）。

方式 C · 上传站

  1. 打开 上传站，填「mod 名 + 备注」，选 zip，点上传（≤100 MB）。
  2. 会给你一个认领码（只显示一次，存好）——用它可改包、撤回。
  3. 维护者审过后，用服务端「过审 → 代提 PR」推进仓库，再走同一条 CI + 审核 + 合并。
包超过 25 MB 时，这条是唯一省事的路。方式 A 有 GitHub 网页 25 MB 硬限； 方式 B 要先装 Git 并下载整个仓库（约 60.9 MB）。上传站不用装任何东西，填表选文件即可。
三种方式的终点不同，别误解。方式 A/B 提的 PR 合并后，包落在仓库的 incoming/ 里等维护者处理；要让它出现在上面这个站上，还需维护者做完兼容、 经上传站审核上线。也就是说：PR 合并 ≠ mod 已上线。

上传规范

一、包的形态
  • 一个 mod 一个目录；目录名 = mod 名字，不要多套一层。
  • pack.json（工坊包）或 plugin.json（插件包）必须在 zip 根；允许一层包裹目录。
  • 单个文件 ≤ 32 MB（引擎 zip 读取上限，超了引擎自带导入路径会拒收）。
  • 整个 zip ≤ 200 MB（引擎 PLUGIN_LIMITS.pluginBytes）。
二、SOURCE.md 要写清的五件事
  • 原件叫什么、从哪来（可追溯的链接或来源）。
  • 原作者是谁（用原作者的名字，不要写成你的）。
  • 原件的许可（如 GPL-3.0-or-later / 未声明）。
  • 你改了什么：具体到文件、数据、数值，不要只写「优化了一些东西」。
  • 自带素材哪来的（自绘 / 从游戏客户端导出 / 第三方，各自标注）。
三、素材与版权
  • 夹带游戏官方素材照收，但必须如实标注 —— 未标注才是问题。
  • 含官方素材的包会在站上醒目标记，并写明「版权归鹰角网络 / Yostar，仅供非商业个人使用」。
  • 原作者明确禁止再分发的，不要提交。
四、CI 会自动挡掉的
判据含义
类型认不出zip 中央目录里既无 pack.json 也无 plugin.json
整档 CRC 失败zip 损坏（传输中断 / 重复压缩）
超过 200 MB引擎装载上限
索引不一致改了 mods/ 下 zip 却没同步 mods/index.json
五、维护者审核会看什么
  • 署名对不对（原作者 ≠ 兼容改写者，要分开写）。
  • 说明里有没有讲清「装上会生效什么」—— 说明包不收，只收能装的真功能包。
  • 会不会和存量包撞 pack.json 的 id（引擎不允许同 id 并存）。
CI 绿 ≠ 已审核。它只能证明「形状对、没损坏」，装不装得上还要维护者在引擎里实测。 合并前缺审批时 GitHub 会直接拦住 PR。
本地自查（可选）

用管理器自带的校验器先过一遍，判据与 CI 对齐：

node tools/mod.mjs check <包目录或 zip>      # 只出报告，不写文件
node tools/mod.mjs import <包> --dry-run     # 看类型与 blocker
提 PR 后 CI 会跑 mod-gate（类型 / CRC / 大小 / 索引一致性）与 mod-compat（静态契约预检）。 两者都绿 + 维护者审批通过，才允许合并。
